# Knowledge Sources — Distillation for the FA3→single-.cu Distillation Agent

Studied two reference repos under `/data-fast/agent/reference/related-works/`:
1. `kernel-design-agents/skills/KernelWiki/` — a structured, queryable Blackwell/Hopper
   kernel-optimization knowledge base, packaged as a Claude Code skill.
2. `mlsys2026-flashinfer-contest-solution/` — HAN Lab "Kernel Mafia" MLSys 2026
   FlashInfer contest WINNING submissions (5 final single-file kernels) + verify harness.

Both are directly informative: KernelWiki shows how to build/query a typed knowledge store
for kernel agents; the contest repo shows what a winning single-`.cu` attention kernel looks
like and how it was produced by an iterative candidate-evolution agent loop.

## PART A — KernelWiki: structure, querying, and how it feeds an in-loop agent

### A.1 Three-layer architecture (Karpathy LLM-Wiki pattern)
- **Layer 1 `sources/`** — raw, immutable summaries. One file per artifact, each with YAML
  frontmatter carrying a unique `id`.
  - `sources/prs/{repo}/PR-{N}.md` — 2179 PR pages (vllm 833, flashinfer 583, sglang 645,
    cutlass 32, pytorch 85, DeepGEMM 1).
  - `sources/contests/{contest}/*.md`, `sources/docs/*.md`, `sources/blogs/*.md`.
- **Layer 2 `wiki/`** — synthesized, cross-referenced pages by `id`. Subdirs:
  `hardware/`, `techniques/`, `kernels/`, `patterns/`, `languages/`, `migration/` (48 pages).
- **Layer 3 `queries/`** — AUTO-GENERATED cross-reference indices (never hand-edited;
  regenerated by `scripts/generate-indices.py`):
  `by-problem.md`, `by-technique.md`, `by-hardware-feature.md`, `by-repo.md`,
  `by-kernel-type.md`, `by-language.md`.
- Supporting `data/`: `schemas.yaml` (per-type required/optional fields), `tags.yaml`
  (80+ controlled-vocab tags; unknown tags rejected by validator), `aliases.yaml`
  (canonical→synonym map, e.g. UMMA→tcgen05, H100/H200→sm90, B200→sm100).
- `artifacts/` — verbatim/extracted/derived code bundles each with `PROVENANCE.yaml`
  pinning upstream SHA + sha256 (verbatim upstream kernel source lives here, retrieved via
  `get_page.py <id> --include-code`).

### A.2 Page schema (the typed-knowledge contract — copy this)
From `data/schemas.yaml`. Each page type has an `id` prefix and required fields:
- **wiki-kernel** (`kernel-`): title, type, architectures, tags, **confidence**,
  **reproducibility**, kernel_types, languages, related, sources, **performance_claims**.
- **wiki-technique** (`technique-`): + prerequisites; reproducibility_minimum = `snippet`.
- **wiki-hardware** (`hw-`): + aliases.
- **wiki-pattern** (`pattern-`): **symptoms**, **candidate_techniques** (the diagnosis map).
- **wiki-language** (`lang-`), **wiki-migration** (`migration-`: from_arch/to_arch +
  blackwell_relevance).
- **source-pr** (`pr-`): repo, pr, title, author, date, url, source_category=upstream-code,
  architectures, tags, techniques, hardware_features, kernel_types, languages, captured_at,
  status, optional `inclusion_reason`, `changed_paths`, `artifact_dir`.

Two enum ladders that we should reuse verbatim in our store:
- **confidence**: `verified` > `source-reported` > `inferred` > `experimental`.
  (`verified` requires `evidence_basis` naming BOTH an official-doc AND upstream-code source.)
- **reproducibility**: `concept` < `pseudocode` < `snippet` < `runnable` < `benchmarked`.
  technique/kernel/language pages MUST be >= `snippet` (validator-enforced).
- **performance_claims** are 6-field records: `gpu, dtype, shape, metric, value, [utilization], source_id`.
  This is exactly the shape we want for storing per-config baseline-vs-candidate latency.

### A.3 Query surface (5 navigation paths) — directly reusable as agent tools
All scripts auto-resolve wiki root via `scripts/_wiki_root.py` (no env var). PyYAML only.
1. `scripts/query.py "<nl keywords>" [--type --tag --repo --language --architecture
   --symptom --confidence --has-code --limit --compact --paths-only]` — unified search.
   - Scoring: title hit +10, tag/technique/hw/kernel/lang hit +5, body count capped +3.
   - **Alias-aware**: every keyword + `--tag`/`--architecture` is expanded through
     `aliases.yaml` before scoring (typing "H200" matches `sm90` pages).
   - `--has-code` checks the page's `artifact_dir` for real source files.
2. `scripts/get_page.py <id|path> [--body-only --frontmatter-only --follow-sources
   --include-code]` — fetch a page; `--follow-sources` prints 500-char excerpts of each
   cited source; `--include-code` dumps the artifact bundle (full upstream kernel source).
3. `scripts/grep_wiki.py "<regex>" [--only wiki|sources|artifacts|all --context --any
   --ext cu,cuh,ptx,py --files-only]` — regex search across bodies AND code artifacts.
4. Pre-built `queries/*.md` indices (read directly when broad).
5. `references/primer.md` (topic map: symptom/feature/technique → canonical page id),
   `references/schema.md`, `references/examples.md` (10 worked NL→command→synthesis patterns).

### A.4 Output contract (how the skill answers — adopt for our profiling/feedback agents)
1. Cite specific pages by path + id. 2. Follow `sources:` to trace claims to PRs/blogs/docs.
3. Respect confidence (flag `inferred`/`experimental`). 4. Include the (validated) code
snippet. 5. Report perf with all 6 fields. The `references/examples.md` "Synthesis Pattern"
is: framing(cite) → mechanism(hw+technique cite) → code snippet → perf evidence → references.

### A.5 What Hopper(sm90)-relevant attention knowledge actually exists here
KernelWiki is **Blackwell-first**; sm90 pages exist only with explicit `blackwell_relevance`.
27 wiki files mention sm90. Relevant pages for OUR FA3-on-Hopper task:
- `technique-warp-specialization` (`wiki/techniques/warp-specialization.md`, archs sm100+**sm90**):
  explicit Hopper vs Blackwell contrast table — Hopper = 4-warp **warpgroup** issuing
  `wgmma.mma_async`, accumulators in **registers**, warpgroup barriers arrive/wait; Blackwell =
  single-thread tcgen05 → TMEM. THE key takeaway for us: FA3 on Hopper uses the warpgroup +
  register-accumulator + wgmma model, with producer/consumer **mbarrier** pairs (data_ready /
  buffer_free) and parity-flip phase tracking — the page gives a full mbarrier pipeline skeleton.
- `technique-ping-pong-scheduling`, `technique-pipeline-stages` (TMA→MMA 3–5 stage),
  `technique-swizzling`, `technique-double-buffering`, `technique-software-exp`,
  `technique-register-budgeting`, `technique-vectorized-loads`, `technique-cache-policy` —
  all tagged sm90 too, all carry a compilable snippet.
- `kernel-flash-attention-4` — FA4 is sm100-only (ping-pong across TMEM, 2-CTA backward,
  software exp). NOT directly portable to Hopper, but the **online-softmax + conditional
  rescale** algorithm and the **software exp2 (Cody-Waite range reduction + degree-4 Horner
  FMA chain)** in `technique-software-exp` are algorithm-level and reusable. Note its caveat:
  software-exp is "NOT recommended on Hopper" (SFU:MMA ratio is balanced on SM90) — useful
  guardrail knowledge.
- `migration-wgmma-to-tcgen05`, `migration-register-to-tmem` — reverse-read these to
  understand the Hopper baseline FA3 is built on (wgmma descriptors, register accumulators).
- `pattern-*` pages map symptoms (low-sm-util, memory-bound, register-pressure, compute-bound,
  tail-effect, pipeline-stalls) → candidate techniques + sources. This symptom→technique table
  is exactly the shape our NCU-feedback agent should emit.

### A.6 The contest layer inside KernelWiki (cross-link to repo #2)
`sources/contests/flashinfer-mlsys26/track-{a-fused-moe,b-sparse-attention,c-gated-delta-net}.md`
each carry a `submissions:` block (rank, participant, score, technique, submission_truth,

## PART B — flashinfer-bench winning submissions: anatomy + how to mine

### B.1 Submission layout (uniform across all 5)
`submissions/<name>/`:
- `config.toml` — `[solution] name/definition/author`, `[build] language(cuda|python)/
  entry_point("kernel.cu::run")/destination_passing_style/[dependencies]/[target_hardware]`.
- `README.md` — definition string + verify command.
- `scripts/pack_solution.py` — reads config.toml, calls
  `flashinfer_bench.agents.pack_solution_from_files(path, BuildSpec(language, target_hardware,
  entry_point, destination_passing_style), name, definition, author)` → writes `solution.json`.
- `scripts/run_local.py` — packs then runs `Benchmark(TraceSet, BenchmarkConfig).run_all()`;
  prints status / latency_ms / speedup_factor / max_abs_error / max_rel_error per workload.
- `scripts/run_modal.py` — remote run.
- `solution/cuda/kernel.cu` OR `solution/python/{main.py,solution.py}` — the ENTIRE kernel.

5 submissions: `dsa-sparse-attention` (cuda), `gdn-decode` (cuda), `moe-fp8` (python),
`gdn-prefill` (python, hybrid CUDA short-path + CuTe-DSL long-path), `dsa-topk-indexer` (python).
Two are single-file CUDA — most analogous to our target.

### B.2 dsa-sparse-attention/solution/cuda/kernel.cu (23 KB, single file) — GOLD for us
This is a self-contained sparse-MLA attention kernel that mirrors what our FA3 output should
look like structurally. Concrete reusable patterns:
- **DPS host entry** `void run(tvm::ffi::Tensor q_nope, ..., output, lse)` — last two args are
  pre-allocated destination tensors; registered via `TVM_FFI_DLL_EXPORT_TYPED_FUNC(run, run)`.
  Host fn pulls `.device()`, the stream via `TVMFFIEnvGetStream`, `.data_ptr()` + `.size(0)`,
  reinterpret_cast to `__nv_bfloat16*`. **Our analog: torch only in mha_fwd host fn** (tensor
  unpack/output alloc) + `TORCH_LIBRARY_EXPAND` registration — same host/device split discipline.
- **Three-kernel chain** in one `run()`: (1) `compact_and_count` ballot+popcount index
  compaction; (2) `dsa_sparse_attn_fused` single-CTA fast path for small rows
  (self-dispatch on `valid_count <= FUSED_BUDGET`); (3) `dsa_sparse_attn_split_reduce_cluster`
  split-KV with **cluster.sync()** producer→reducer handoff and LSE-weighted merge.
- **Online softmax in log2 space** (the FA3 math, bit-identical to track requirement):
  `sm_scale_log2e = sm_scale * 1.4426950408889634f`; per-tile
  `m_new=max(m,logit); scale=exp2f(m-m_new); pp=exp2f(logit-m_new); acc=acc*scale+pp*v;
  l=l*scale+pp`. Final `lse = m + log2f(l)`. **This is exactly the numeric recipe greedy
  decoding must match** — our correctness gate should compare output AND lse with this form.
- **Split-KV reduce via LSE weights**: `global_m=max(lse_s); w_s=exp2f(lse_s-global_m);
  out = sum(w_s*partial_s) / sum(w_s); final lse = global_m + log2f(denom)`. Reuse for our
  decode/long-context splits.
- **Vectorized SMEM staging**: cast global+SMEM to `int4*` (128-bit, D_CKV/8 elems) for
  coalesced bf16 loads; `__align__(16)` SMEM; strided job loop `for(job=tid; job<count*INT4;
  job+=512)`.
- **Dynamic SMEM + non-portable clusters opt-in** (documented as "blockers" BL-... in the
  header): `cudaFuncSetAttribute(..., cudaFuncAttributeMaxDynamicSharedMemorySize, 72KB)` and
  `cudaFuncAttributeNonPortableClusterSizeAllowed, 1` for cluster size 16 (>portable cap 8),
  set once per device behind a mutex+map guard. **This is the kind of host-side setup our agent
  must remember to emit** (>48KB SMEM needs opt-in; FA3 tiles will hit this on Hopper too).
- **Persistent workspace pool**: process-global struct grown on demand via `cudaMallocAsync`
  on the active stream, mutex-guarded, amortised across repeated `run()` calls (the evaluator
  calls run() per workload). Good pattern for scratch (split partials, LSE) without per-call malloc.
- **Header comment = a complete provenance/decision log**: names the promoted candidate node
  ("Plan v6 R1 PROMOTED"), records arith/geom speedups under eager vs NCU vs graph-capture
  harnesses, lists the blocker IDs that constrained the design. This is how the evolution loop
  serialized its learning INTO the artifact — we should embed similar provenance in our .cu.

### B.3 gdn-decode kernel.cu — more reusable idioms
- Header documents version lineage ("v11 2-row pipeline ... reduces live register state vs v7")
  — explicit **register-budgeting** as the optimization axis, barrier-free design, fixed
  256-thread/8-warp layout, work split 4 CTAs per (batch, v_head). `warp_reduce_sum` via
  `__shfl_xor_sync` butterfly is the standard reduction primitive (appears in both kernels).

### B.4 Verify / measurement harness (repo root verify.py, scripts/smoke_benchmark.py)
- `flashinfer_bench` primitives: `TraceSet.from_path(dataset)` → `.definitions/.workloads/
  .solutions/.traces`; build a per-solution `TraceSet`; `Benchmark(ts, BenchmarkConfig).run_all()`
  returns traces with `.evaluation.status` (PASSED), `.evaluation.performance.{latency_ms,
  reference_latency_ms, speedup_factor}`, `.evaluation.correctness.{max_absolute_error,
  max_relative_error}`.
- **BenchmarkConfig knobs we should mirror**: `warmup_runs, iterations, num_trials,
  use_isolated_runner`, and per-definition correctness tolerances `atol/rtol/required_matched_ratio`
  (moe_fp8 uses atol=1.0, rtol=0.3, required_matched_ratio=0.9 — i.e. tolerances are
  config-specific, not global). `--fast` profile = warmup 1 / iter 5 / trials 1 / limit 2.
  Full = warmup 3 / iter 50–100 / trials 3–5. **Verify FIRST then time** is baked in
  (status PASSED gates speedup).
- Pinned env: torch 2.12 cu132, triton==3.6.0, flashinfer-python 0.6.8, ninja, DeepGEMM for
  FP8 paths. (Ours: torch 2.11 cu130, CUDA 13.0 — close enough; mind ABI.)

## PART C — Concrete design for OUR agent's typed knowledge store + in-loop distillation

### C.1 Knowledge typing (map the task's 3 types onto KernelWiki's schema)
Adopt KernelWiki's frontmatter+id+confidence+reproducibility model, three page types:
- **kernel-specific** (`ks-`): facts about THIS FA3/vLLM kernel — the mha_fwd signature, the
  exact arg layout of `torch.ops._vllm_fa3_C.fwd`, per-config shapes vLLM actually issues
  (prefill vs decode, head dims, page sizes, causal flags), SMEM-opt-in needs, wgmma/TMA
  descriptor details, the online-softmax-in-log2 numeric recipe (B.2), tile/warp layouts that
  worked. Fields: `config`(shape/dtype), `area`, `confidence`, `reproducibility`, `source`
  (candidate id / SASS diff / NCU run), `code_snippet`, `verified_against_baseline: bool`.
- **profiling** (`pf-`): typed NCU/Nsys/compute-sanitizer findings → actionable feedback,
  keyed by op + symptom. Reuse `pattern-*` shape: `symptom` (e.g. low-mma-util, smem-bank-
  conflict, register-spill, uncoalesced-ld, sync-stall, race/init from compute-sanitizer),
  `metric_evidence` (the 6-field perf record + the specific NCU counter), `candidate_techniques`
  (cite kernel-specific/algorithmic notes), `config_scope` (which vLLM configs it applies to).
- **algorithmic** (`alg-`): hardware/technique knowledge — warp-specialization (Hopper
  warpgroup+register+wgmma+mbarrier model), pipeline-stages, swizzling, split-KV+LSE reduce,
  online softmax, software-exp (with the "skip on Hopper" guardrail), cache-policy,
  register-budgeting. Seed these by importing the relevant KernelWiki technique snippets.

### C.2 Store layout (mirror the 3-layer pattern, smaller)
- `knowledge/sources/` — raw candidate provenance, NCU report dumps, SASS dumps,
  compute-sanitizer logs, baseline latency tables (one file per candidate/profile run, with id).
- `knowledge/notes/{kernel-specific,profiling,algorithmic}/*.md` — synthesized typed pages
  with YAML frontmatter (id-prefixed, confidence, reproducibility, sources, config_scope).
- `knowledge/index/` — auto-generated `by-symptom.md`, `by-config.md`, `by-technique.md`
  regenerated by a generate-indices step after each loop (don't hand-edit).
- A tiny `query.py`/`get_note.py`/`grep_notes.py` trio (port KernelWiki's, drop Blackwell
  vocab, add `--config`/`--symptom` filters and an `aliases.yaml` for H200/sm90a/headdim names).
  Reuse the alias-aware scoring (title+10/tag+5/body) and `--follow-sources`/`--include-code`.

### C.3 In-loop distillation flow (generate→verify→profile→optimize→learn)
Per iteration, after a candidate is evaluated, emit typed notes (this is "in-loop distillation"):
1. **Generate** candidate `.cu` (sub-agent queries the store first: `query.py --config <shape>
   --symptom <last-bottleneck>` + relevant `alg-`/`ks-` notes injected into the prompt).
2. **Verify FIRST** (anti-cheating + correctness): toolkit-only include scan + nm/ldd on the
   built .so; then numeric compare output+lse vs baseline `_vllm_fa3_C.fwd` across all vLLM
   configs; then the 100-token greedy-decode equivalence gate. Gate speedup on PASSED.
   → write a `ks-` note: which configs passed, the numeric recipe confirmed, tolerances used.
3. **Profile** (NCU/Nsys): the parser (component 2.1) emits CONCISE per-op feedback in the
   `pf-` symptom→evidence→candidate_techniques shape; store as a `pf-` note keyed by config.
4. **Optimize**: next candidate's prompt is built from the top-ranked `pf-` symptom + the
   `alg-` technique it points to + any `ks-` note that says "X worked/failed for this config".
5. **Learn / promote**: on a win, append a provenance block to the champion .cu header (a la
   B.2: promoted-node id, per-config arith/geom speedup, blocker IDs) AND bump the relevant
   note's `confidence` (inferred→source-reported→verified once measured) and
   `reproducibility` (snippet→benchmarked with the 6-field perf record). Failures are recorded
   too (negative knowledge: "software-exp regressed config Y by N%") so the loop stops retrying.
6. Checkpoint after every step: persist store + champion + evolution-plot data points
   (per-config latency vs candidate id) so resume re-reads the typed store, not just code.

### C.5 Direct mechanics to copy (cheap wins)
- Controlled-vocab `tags.yaml` + `aliases.yaml` + a `validate.py` that rejects unknown tags and
  enforces required fields per note type → keeps the store machine-queryable for sub-agents.
- `_wiki_root.py`-style root resolver so query tools work from any sub-agent cwd (note: our
  sub-agents reset cwd per bash call → use absolute paths or the resolver).
- `query.py` scoring + `--follow-sources` + `--include-code` so a generation sub-agent can pull
  a note AND its backing code/profile dump in one call.
- Auto-generated indices regenerated each loop, never hand-edited.
